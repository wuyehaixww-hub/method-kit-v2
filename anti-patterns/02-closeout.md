# L3 反例 · 02 收尾（A-04..A-06 · A-20 · A-22）

> 反例 = **真实发生过的失效**，带实测数字 + 日期 + 出处。数字会漂 —— 本册的数字只作「当时的观测」，不作当前承诺。
> 每条四段：**现象** / **根因** / **正解（指向 P-NN）** / **怎么早发现**。
> 选条标准：**三个不同根因各一条**，不把一个根因写成三条（否则反例册变成同义反复）。

## A-04 收尾只跑脚本，状态真源没写回

- **现象**（本方法仓 2026-10-30 12:56 实测）：三处同时存在的版本号 —— `VERSION` = `0.2.1-dev`（tag `v0.2.1-dev` 也在）· 状态行仍写 `0.2.0-dev` / tag `v0.2.0-dev` · `README.md` 更写着 `0.1.0-dev`。**三处各说各的，而同一时刻 `check-kit` 17 md / 0 FAIL / 0 WARN、`selftest` 20/20、`cold-start` OK —— 全绿。** 上一棒其实已经点出过「说发 `0.1.1-dev`，但没定 `tag` / `CHANGELOG` / `WORKSPACE-NOTES` 三处同步」补了一次，下一棒又漂。
- **根因**：「更新当前状态」在收尾清单里是一句**散文动作**，而版本号是**可机械比对的字符串** —— 只有被门禁覆盖的那一处（探针 6 只比 `VERSION` ↔ `CHANGELOG` 顶部）每次都被改，其余两处靠记忆。**同一个事实在三处写全 = 三处都要改，而人只会改他正在看的那一处。**
- **正解**：P-06（完成标准 = 真源闭合）+ P-10（数字只在一处写全，其余写指针）。
- **怎么早发现**：收尾后 grep 一次当前版本号：**命中 > 1 处且不全等 → 已有漂移**。本方法仓当时实测 `0\.1\.0-dev|0\.1\.1-dev` 全仓 **13 处命中**，其中 1 处是「活」的当前状态行 —— 活着的那一处才是最贵的。

## A-05 留后项搬一次家就没了

- **现象**：2026-10-30 台账从一个仓搬进另一个仓（新建仓），丢了一条 **D1a**（「与另一个仓合并」那条）；新仓**全仓 grep = 0 命中**、且当时**没人发现**（自检单 `### A3` 记的就是这件事）—— 后来由外部独立复核抓出、随台账搬仓一并补回（补回后该行尾仍带「正文未读 = 缺口」的伤疤）。全程没有任何一步报错：文件在、格式对、门禁绿。出处 = 自检单 `### A3` + 台账 §5 首行。
- **根因**：搬运被当成「复制文件」而不是**逐条交接**。丢的条目不会让文件小到被容量门看出，也不会让引用探针变红 —— **「已经不存在的 ID」比「引用错的 ID」更难被发现**（后者探针 2 会红，前者没有任何痕迹）。
- **正解**：P-07（新开放项进唯一登记面 + 到期触发）+ P-08（搬前列清单 → 搬 → 再列 → 对比条数）。**别把本条与 `P-31` 混起来**：本条 = 搬运**丢内容**（数条数能抓），`P-31` = 指针不再可达（grep 能抓）—— 留指针救不了漏抄的条目。
- **怎么早发现**：任何「搬家 / 归档 / 合并」动作，**先数条数再动手**；两次清单条数不等就停。对「唯一台账」尤其如此 —— 它没有备份。

## A-06 同一件事写两处，就只会改被看见的那处

- **现象**（两次实测）：① 另一项目 2026-10-11 实测：「当前第一读」有**两处**书写点（索引头部 + 条目段行），只改了头部 → 第二处 stale（本方法仓今天**同样两处**：索引头部 + 状态行，靠「两处必同步」这句话维持）。② 本方法仓 2026-10-30 自认：汇报写「9 条指针」，清单里实为 **8 行** —— 9 是「全仓去重计数」，不是「表里行数」。
- **根因**：同一事实有多个书写点，而**改的人只看得见自己正在读的那一处**；两处不一致时**没有任何信号** —— 两处都「读得通」。这与记性无关，是结构问题。
- **正解**：P-06（只在一处写全）+ P-09（多书写点状态词全仓 grep）+ P-10（数字必经命令重测）。
- **怎么早发现**：写下「当前 / 最新 / 已收口 / 下一棒 / 第一读」这类状态词时问一句「**这个词在仓里有几处**」；答不出唯一 = 它明天就会漂。
## A-20 归档搬走了一段，而「指向旧归档的那一行」恰好就在那段里

- **现象**（2026-11-02 实测，作者自己踩的）：按 `P-08` 把 `0.4.0`–`0.7.0` 五段搬进归档后，变更日志里对**上一份归档**的唯一指针 —— 原本写在 `0.11.0-dev` 段里的「…（5 段，逐字）→ 该文件」那一行 —— **随段一起搬走了**。结果：主文件 `grep` 那份归档名 = **0 命中**，读者从主文件再也到不了那份归档；而当轮**所有门禁都是绿的**（文件在、指针在被搬去的那份归档里、容量也对）。
- **根因**：搬段时只看「这段到没到新址」，没看「这段里有没有别人要用的**路牌**」—— 被搬的内容**同时是别人的指路牌**。失败不报警：没有任何东西「坏掉」，只是某条路从主文件上消失了。
- **正解**：`P-31` —— 删 / 搬之前做**双向审计**：出向（这段引用的真源仍可达）+ 入向（别人指向这段的指针要改址）。落点 = 归档清单加一列「本段是否含指针」，搬后 `grep` 每个被搬走的名字**必须仍命中**。
- **怎么早发现**：搬完立刻 grep 一遍**每个被搬走的归档名 / 旧标题**；主文件 0 命中 = 有一块路牌被搬走了。

## A-22 五段搬进了归档，归档索引里没有那一行

- **现象**（本方法仓 2026-11-02 搬、2026-11-04 才发现）：按 `P-08` 把 `CHANGELOG` 的 `0.4.0`–`0.7.0` 五段搬进 `session-notes/archive/`，文件在、容量也对、**且从主文件两跳仍能走到它**（`CHANGELOG.md` 直接指的只有 `0.8.0` 归档；0.4.0 归档的唯一直接指针在 `CHANGELOG-0.8.0-0.10.0.md` 里）；但**归档索引里没有这五段的那一行**。**两天**没人发现 —— 因为没有人需要从索引去读它，直到下一次归档要「搬前数条数」时，才发现索引对不上磁盘。
- **根因**：把「归档」当成一个**动作**（移动文件），没当成一个**完成条件**。「搬完了」被默认成「文件到新位置了」，而真正要用的是「**账上有这一笔**」。`P-31` 抓不到它（指针两跳可达，按它的字面义务并不违反），`P-08` 的「数条数」也抓不到（搬前搬后条数相等，只是账里少一行）。
- **正解**：`P-33`。**动作**：搬完当场补上索引那一行（五列），再回查「索引 ↔ 磁盘」两边是否一一对应。**分工**：本条不是「指针断了」，是「账没记」—— 补指针救不了没记的账，数条数也救不了。
- **怎么早发现**：归档后**从索引反查磁盘**（不是从主文件）：索引每一行都 `Test-Path` 得到、磁盘每个归档件都在索引里有一行。两边不等就停。
