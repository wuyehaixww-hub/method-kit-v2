# L0 原则 · 05 取料（冷启动 / 回退阶梯 / 容量 / 读取协议）

> 本册 = 「怎么用最少的上下文，可靠地取到该取的东西」。条目：`P-01`..`P-05` · `P-26` · `P-30` · `P-32`。
> **阈值不写在本册**：真源 = `kit.config.json`（`coldStart` / `capacityTiers` / `sectionRead` / `quotas`）。本册只写**规则与判据** —— 数值复述三处必然漂成两套答案。
> 每条四段：**规则**（做什么）/ **为什么** / **反例**（不做会怎样）/ **怎么查**（机械点或「半机械」的诚实标注）。

## P-01 冷启动最小面 + 硬门


- **规则**：新会话第一屏只许三件 —— **入口壳**（行为约束 + 场景路由）/ **当前状态** / **索引**。三者 UTF-8 字节和 ≤ `coldStart.limitBytes`；**余量 < `coldStart.forceArchiveMarginBytes` 即强制归档**（是入口动作，不是「提醒」）。
- **为什么**：上下文是每会话唯一不可回收的资源；三件是「能开工」的最小充分集。上限的作用是**让超支可被发现**，不是让文件变小 —— 一个没有门的「建议」等于没有。
- **反例**：A-01（「余量还有」是假象）。
- **怎么查**：`node kit/scripts/cold-start-size.mjs` —— 三态：缺件 `FAIL` / 超门 `FAIL` / 余量不足 `WARN 强制归档`。

## P-02 回退阶梯 R0–R3


- **规则**：取料顺序固定 —— **R0** 场景路由 / 索引命中 → 读指针；**R1** 未命中 → 抽大纲（`^## `）按节取；**R2** 大纲未命中 → 任务词 grep 正文（扫描面固定：tracked 全集减归档）；**R3** 仍无 → 换词重试一轮 → **报用户 + 登记缺口**。**没找到 ≠ 不存在，禁自创。**
- **为什么**：薄壳只承诺「可恢复」、不承诺「完备」—— 它必然不含全部规则。缺一条固定阶梯，agent 遇到空白就会**自己造一个规则**，这是「省上下文」最贵的失败方式（省下的字节会以更贵的代价还回来）。
- **反例**：A-03（同型：靠「声明过」而不是「查得到」来保证覆盖）。
- **怎么查**：**半机械** —— 引用可解析性由 `check-kit` 探针 2（引用必须存在）+ 探针 9（条目必须被引用）兜；阶梯本身靠 review，不假装有门禁。

## P-03 容量四档 + 硬顶


- **规则**：按用途分四档 —— **A 整读型**（agent 会整文件读）/ **B 按需型** / **C 索引清单型** / **D 抽屉**（逐字归档，不设档位与硬顶）。阈值与硬顶真源 = `capacityTiers`。跨档固定两条：**任何档 > `maxLines` 行必须「一条目一行」可寻址**；**单行 ≤ `maxLineChars` 对全部档（含 D）仍适用**。**硬顶只适用 A/B/C。**
- **为什么**：上限的目的 = **让「没读完」可被发现**。没有硬顶的查询型文档会无限叠加（A-02）；有探针但只在声明了才校验，最大的文件往往正是没声明的那个（A-03）。
- **怎么判档**：这文件 agent 会**整读**吗 → A；只在**查的时候翻一段** → B；本质是**清单 / 索引** → C；**原文逐字、只作证据** → D。**判不准就取更严的一档**（代价不对称：档位过宽 = 读不完，过严 = 多拆一次）。
- **反例**：A-02（无硬顶 = 无限叠加）/ A-03（声明式校验 = 放过未声明者）。
- **怎么查**：`node kit/scripts/check-kit.mjs` 探针 3 —— 分档 + 硬顶 + 行数 + 单行长度，一次判完。

## P-04 按节读协议


- **规则**：任何超过 `sectionRead.thresholdBytes` 的文件**必须**在前 20 行内声明「按节读」（标记字 = `sectionRead.marker`），否则探针 `FAIL`。**节图由 `kit/scripts/read-plan.mjs` 即时生成；禁止把行区间写死进文档** —— 行区间会腐烂，且探针只能查节号存在、查不出行号错。
- **为什么**：读取工具有单次上限，超限**静默截断**（示例：DSH 的 `read` 约 50 KiB / 2000 行 / 单行 2000 字符；在脚本里调它时连截断页脚都没有）→ 把截断当全文是最高频的「假读全」。声明把「不要整读」变成契约，探针把它变成硬门。
- **反例**：A-03（「只在声明了才校验」= 不声明就放行，于是最大的文件正是没声明的那个）。
- **怎么查**：`check-kit` 探针 7（前 20 行缺标记 → `FAIL`）+ `node kit/scripts/read-plan.mjs <file>` 出节图。

## P-05 配额制 = 强制减法


- **规则**：**任何会无限增长的东西都要有配额**（冷启动字节 / L0 条目数 / inbox 条数；真源 = `coldStart.limitBytes` · `quotas`）。到顶后**先退役或合并一条，才能加一条**。
- **为什么**：没有配额的集合只会单调增长，而「该删哪条」永远比「再加一条」难 —— 配额把难的决定**提前到加的那一瞬**。注意它逼的是**合并**，不是逼你拆细（把行数当判据会拆出一堆更碎的东西）。
- **反例**：A-02（查询型文档无硬顶 → 246.7 KB 只出一条 WARN 就通过）。
- **怎么查**：`check-kit` 探针 10（L0 条数 > `quotas.l0MaxEntries` → `FAIL`；若你设了 `inbox/`，同时查其条数）。

## P-26 copy 件的完成条件 = 裁到 0 处


- **规则**：凡把 kit 的模板 / 脚本**照抄**进另一个仓的件（= copy 件），交付前必须**就地裁剪**；判据按**件的形态**分两类，别用一把尺量到底：
  - **指针形态**（`CLAUDE.md` / `WORKSPACE-NOTES.md` / `docs/README.md` / `INTAKE.md` 这类 Markdown）：占位符换成该仓真实值（换不了就删整行），指向该仓**不存在文件**的引用删整行；判据 = 裁剪体检的**两处计数都为 0**。
  - **配置形态**（`kit.config.json` 这类纯数据）：删的是**键**不是行；判据 = 逐个删键后冷启动门仍 `OK`（删到「再删就红」= 最小面），且**阈值三键不许删**（删了门会失效）。
  
  **目录可以先不建，文件不行**；**merge / 改写都不叫 copy**（协议说 copy 就是 copy，然后裁）。
- **为什么**：模板带着**它来源项目的形状** —— 路由表按那边的文件名写，而目标仓里没有那些文件。目标仓能拿到的门通常只查「件在不在 + 字节和」，**不解析内容**（`P-01` 的硬门只量体积），所以死指针一路绿（`A-17`）。正确性一旦落在「执行者自觉」，自觉的会越权改成 merge，不自觉的交付一个空面 —— 两种都不报错。
- **反例**：A-17。
- **怎么查**：`node kit/scripts/trim-scan.mjs --root <项目>` → 要看到「占位符 0 处 · 死指针 0 处」+ `exit 0`；它**第一行**点名项目根，不对 = 量错对象（`A-16`）。**半机械**：只判**反引号里的引用**与**代码块里的命令行路径**；正文裸路径 / md 链接 / 锚点**不判** —— 那部分靠交付前的人工问句「随便抽三行指向的文件，打得开吗」。
## P-30 「读全」要可证：引用内容 ⇒ 拿得出完整覆盖的读记录


- **规则**：文档 / 报告里**引用了某文件的内容**（引原文、断言行数、断言「已读全」）⇒ 该文件必须有**完整覆盖**的读记录 —— 一次读完，或按偏移分段、**区间合并后覆盖 `1..total`**。只读了部分 → 二选一：**补读**，或**明写「只读了 §X，未读 §Y，影响是…」**。`total` 取**读的那一刻**的结果（之后文件变长不算你没读）。**小文件同样适用** —— 写「全 N 行」也是一句话的成本，别拿「反正读完了」当记录。**不适用**：引用不涉内容时（只提文件名 / 只判存在性 / 只判它有没有某个标题）。
- **为什么**：`P-04` 只说「别把截断当全文」—— 那是**纪律**，不是**载体**。读的人自己知道读没读全，**别人看不出来**；而建在被截断文本上的结论，错法是「漏掉文件后半的那一节」，前半读起来完全正常 —— 失败不报警。
- **反例**：`A-19`（按「读开头 30 行」下结论，失效恰好落在没读的那一节）。
- **怎么查**：**半机械** —— ① 报告里每条「读了 X」旁边写**覆盖形态**（「全 312 行」/「§3–§5，共 140 行」），写不出来 = 没读全；② 有会话轨迹的环境可核**读取工具**的调用区间是否覆盖 `1..total`（口径 = 通用；本方法仓没有配套脚本，`P-15` 不假装有）。

## P-32 拆卷前先答四问；按读者切，不按原文节号切


- **规则**：某文档 / 册 / 表被认为「太大、读不下」时，**按序答四问，前一问不过不许进下一问**：
  1. **按节读（`P-04`）够不够？** 够 → **不拆**（零成本先试，别跳过）。
  2. **是不是「一次读不完」**（单份超过「一次完整读取」阈值）？是 → 拆。**阈值从 `kit.config.json` 取（`sectionRead.thresholdBytes`；实测读上限与之不同时先改配置，别在文档里写死字节）**。
  3. **是不是「两个读者 / 两种更新节奏」**（一半必须现在知道、一半查的时候才要）？是 → 拆，**且主件降为路由页**。
  4. 都不是、**只是大**？ → **不拆**。

  **硬约束（只在第 2 / 3 问成立、真要拆时适用）**：
  - **按读者 / 问题切，禁按「原文节号」切**（按节号切 = 跟着原结构走 = 迟早再分流一次）。
  - **路由页不应是家族里最大的那一件**（更稳的口径 = ≤ 各卷中位数）。
  - **路由页是第二书写点**（`P-25`）：须有机械校验或过期自检（`P-14`）。
  - **拆是单向门**：合并要重排 ID、重指所有交叉引用 —— 所以必须已试过第 1 问。
  - **冷启动面永不拆**：路由页的固定税会被每个会话重复支付。
- **为什么**：拆错不是「白干」，是**制造新成本** —— 路由页漂移、跨卷引用断、查一个全景问题要跳 3–4 次；反复搬家还会让探针面静默变窄（分卷后写死路径的门禁只扫到一部分）。而「只是大」不构成拆的理由：按节读的固定成本远低于拆分的固定税。
- **反例**：`A-21`（按量拆卷 → 路由页自己长成最大卷、垃圾桶卷、有效性闸 0 次执行）。
- **怎么查**：**半机械** —— 机械：路由页字节 vs 家族最小卷 / 中位数（`check-kit` 的单册上限可复用；无专门探针）；死链 / 落位（`check-kit` 探针 5 + `read-plan` 现抽）。人工：「是不是两个读者」只能人判；「有没有制造新成本」看拆分后**第一次查全景问题**跳了几次。
