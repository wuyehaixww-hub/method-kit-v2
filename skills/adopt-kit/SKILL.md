一套治理面的价值不在「全」，在**刚好**：多了没人执行，少了没人记得。本 skill 的产出是一份**决定**（装什么 / 不装什么 / 何时加 / 谁拍板 / 用哪套词），不是一个模子。

## 何时用

- 要把 kit 装进一个**新项目**，或给**既有项目**补治理面。
- 觉得现有治理太重（写不完）或太轻（老踩坑）。
- 换人 / 换会话接手，需要知道「这里为什么只有这几个文件」。
- 项目里出现了 kit 的编号 / 术语，读起来像外来的（→ 见「术语校准」）。

## 第 0 步：先判「绿地」还是「既有」（判据，不靠印象）

**判据**：这个仓里**有没有「能跑或能对外」的东西**（代码 / 构建产物 / 发布物 / 真实数据 / 已有自己的文档体系）？
**不看是谁写的** —— AI 写的代码也是代码；判「有没有东西」，不判「谁的手笔」。
- 有（有可执行代码 / 有发布物 / 历史提交 > 2 / 已有自己的文档体系）→ **既有**
- 没有（空目录 / 刚 `git init` / 只有几份 md）→ **绿地**

用 `project-scan` 的事实判，不用感觉：`文件 0–几个 · 提交 0–2 · 无测试 · 无 CI · 无发布信号` = 绿地（扫描器的推断段此时基本为空，那句「没扫到明显信号 → 默认按 oneoff + tiny 起问」就是绿地的入口）。

| 差异点 | 绿地 | 既有 |
|---|---|---|
| 第 4 问「目录里已有什么」 | **跳过**（答案恒为「空」） | 照问 |
| `--update-baseline` | **不适用**（无存量） | **仅当你要把 `check-kit` 也装进目标仓时**才需要先冻结；本 skill 默认不装它（见「不做」） |
| 默认装几件 | **至少 3 件**（`coldstart` / `agency` / `intake` 常驻）；其余件**按它自己的 `to_enable_when`** 决定，**不按轴的并集** | 按候选轮两档 |
| 额外一步 | **定「第一周交付物」** —— 治理面装完那天项目还没有任何产出；不设交付物，治理面会自我复制 | — |

绿地不是另一套流程，是同一套的**分支**：少问一问、多一个交付物。

## 五步

1. **扫事实**：`node kit/scripts/project-scan.mjs --root <目标目录>`。它给事实 + 标 `[?]` 的推断；**推断只用来提问，不当结论**。绿地里「扫不出东西」**本身就是结论**（别把空目录读成「再等等」）。**本协议里所有 `kit/…` 路径都相对 kit 根，不是相对你的项目** —— 站在项目目录里直接敲 `kit/scripts/…` 是找不到的。
2. **开放轮（7 问，不给选项）**：见下表。**每题都有默认值 —— 跳过 = 采纳默认，不产生负债感**；一轮问完，别边问边给方案。绿地跳过第 4 问。
3. **候选轮（才给选项）**：用轴取值跑 `node kit/scripts/adopt-plan.mjs --horizon=… --risk=… --scale=… --agency=…`。**它的输出是候选池，不是结论**（轴的并集）。逐件用它自己的 `to_enable_when` 过滤 → 这才是「**最小**」档；再把 scale/risk 各升一档 = 「标准」档。每档写清**放弃了什么**，只问一句：「选哪个 / 要加哪件」。
   **对账（矩阵给的是候选，不是结论）**：逐件再用它自己的 `to_enable_when` 过一遍 —— **专有触发优先于轴的粗筛**。`include` 回答「这条轴下值得看哪几件」，`to_enable_when` 回答「这一件的条件到了没有」；两边不一致以 `to_enable_when` 为准，被筛掉的件连同它的触发写进「不装」。**别把 `adopt-plan` 的输出当最终答案**（它只读 `include`，读不到 `to_enable_when`）。
4. **建面 + 记录**：装 `copy` 类件（照 plan 的「拷」行）。**copy 件 = 照抄再裁剪**（merge 与改写都不算 copy；三条动作与判据 = `coldstart-intake` 第 1 步，`INTAKE.md` 与冷启动三件同样适用）；`guide` 类件按 plan 的「做」行动手写 3–5 行。然后填 `kit/templates/INTAKE.md.template` → 目标项目的 `INTAKE.md`（**含决策权表与术语**；绿地另写「第一周交付物」），并在 `WORKSPACE-NOTES.md` 的「当前状态」里加一行指向它。建冷启动面时调 `coldstart-intake`（不在此重复它的步骤）。 **装了 `progress` 类件时**：把 `kit/templates/grill-decisions.md.template` 与 `kit/templates/closeout-todo.md.template` 拷进目标项目的记录区，并把「什么时候写」写进入口壳 —— 一轮里有 ≥2 个待裁问题 → 决策面；收尾有 ≥3 项要延后 → 登记面。
   **源不在手边时**：`copy` 件的模板 / 脚本没拷过来就是没有 —— **不许手写替身**（那就不是 copy 件了）。标「未落地 + 缺哪几个文件」，写进 INTAKE 的验收列，**别留空、也别假装装上了**。
5. **验收 + 复审**：逐件跑 plan 给的「验收」；人工判据那几件，当场问一句就能答 = 通过。把复审触发抄进 INTAKE `§5`。
   **装完告诉用户「发生了什么变化」**（事实，不做评分 —— 好坏由他判、由时间判）：新增了哪几件 / 每次开工固定多读几份（**逐份清单**，不是只报总数）、多少字节 / 每次收尾多一张什么表。**装前不强制取基线**：多数项目装前没有可比的口径（没有三件、没有门禁、没有收尾动作），硬取会得到一串「不适用」。

## 开放轮 7 问（每题带「我为什么问」与「跳过时的默认」）

| # | 问题 | 我为什么问 | 跳过默认 |
|---|---|---|---|
| 1 | 做到什么程度算完成？（做完就扔 / 会改几次 / 长期养） | 决定寿命轴，它是唯一一笔大减法 | weeks |
| 2 | 最怕哪种坏结果？（无所谓 / 改坏对外契约 / 丢数据） | 决定门禁强度，不决定件数 | none（但扫描器报持久化/发布信号时默认升 contract） |
| 3 | 谁拍板？（你 / 你听建议 / AI 执行你抽查） | 决定分权与解释密度，**不改变件数** | copilot |
| 4 | 现在目录里已有什么？（空 / 有码 / 有文档 / 有历史包袱） | 决定要不要先 `--update-baseline` 冻结存量 | 按扫描结果（绿地 = 空，不问） |
| 5 | 愿意为「以后省事」现在付多少？（0 / 半小时 / 半天） | 0 → 只装 coldstart；半小时 → 标准；半天 → 长期 | 半小时 |
| 6 | 会有几个会话 / 几个人碰它？ | 3 个会话或 2 个人 → relay 从「不装」变「装」 | 1 人 1 会话 |
| 7 | 有没有不可逆的东西？（发布 / 外部用户 / 真实数据） | 有 → adr 必须装，risk 升一档 | 无 |

## 决策权表：`agency` 轴的落地（不是四个字）

第 3 问只给一个**默认档**；真要用得起来，得回答「**哪几件事谁拍板**」。第 4 步填 INTAKE 时，按 5–7 个流程各填一档：

| 流程 | AI 跑 / AI 提议你批 / 你跑 |
|---|---|
| 改代码（实现 / 重构 / 修 bug） | |
| 改文档 / 规则 / 判据 | |
| 提交 / 合并 | |
| **发布 / 打 tag / 部署** | **固定「你跑」** |
| **删文件 / 搬目录 / 改结构** | **固定「你跑」** |
| **改对外契约 / 数据格式** | **固定「你跑」** |
| 跑门禁 / 验收 / 复核 | |

**默认值从 `agency` 推**：`human` → 大多「你跑」，AI 只提议；`copilot` → 默认「AI 提议你批」，纯机械项（跑门禁 / 自测 / 计数）「AI 跑」；`agent` → 默认「AI 跑 + 事后抽查」。
**三条不可放宽（[硬]）**：发布点 · 删结构（含**退役 / 合并**）· 改对外契约 —— **与 agency 无关，永远「你跑」**。理由：这三件不可逆，而「不可逆」不随你放权程度变化；把它写进表，是为了让「AI 能自己发版」这种默认**根本没机会形成**。
**判不出时怎么办**（不懂工程的人一定会遇到）：别问他「这算不算改对外契约」——先让 agent 用一句人话说清「**谁会受影响、这个影响可不可逆**」，再让他点头。**判不出 ≠ 可以放行**；也不许替他判。
**减法**：写不出「**本会话或第一周内**能指认的一个具体动作」的流程 → **删掉那行**。表不是清单，删行比填满重要。
**但三条固定行不受减法约束**：它们在第一天本来就常常没有实例（正因为如此才要写死）—— 按字面删掉，这条硬约束就失去了落点。无实例时保留行 + 标「长期不触发」。

## 术语校准（装进来时，别把两套词一起搬）

1. **编号不进口**：项目正文不出现 `P-NN` / `A-NN` / `L0..L3`；要留出处就写一行「依据：method-kit P-xx」。**判据**：`grep -E "P-[0-9]+|A-[0-9]+"` 在项目里应只命中「依据：」那几行。
2. **一个概念一个词**：INTAKE 里记「本项目管它叫什么」（kit 的『收尾』→ 项目的『会话末同步』）。记下来的目的不是翻译，是**防止同一个东西两个名字**。
3. **让路**：项目已有的词优先，kit 的术语让路。**移植不是改名运动** —— 为了对齐 kit 去改项目里已经在用的词，是拿读者换整齐。

## 三条硬纪律

- **说不出「防的是哪种坏结果」的件，不装**（写不出 INTAKE 那一行，就删掉这行）。
- **第一轮不给选项**；选项只在第二轮出现，且必须写「放弃了什么」—— 只报好处 = 诱导。
- **跳过 = 默认**：用户不答，就按默认走，并在 INTAKE 里记「按默认」，别追问第二遍。

## 反例（都是真实会发生的）

- 把大仓的整包治理搬进一次性脚本目录 → 第一天就写不完，第二天全废。
- **绿地第一天就把 9 件装齐** → 治理面成了项目本身（两周后没人执行，也没人敢删）。
- 「先建 88 篇文档再写第一行代码」→ 同上，只是更慢。
- 问 20 个问题、每题给 4 个选项 → 用户在第二题就开始敷衍，答案质量反而更差。
- 用扫描器的推断直接定档（「我看到 sqlite 所以你是长期项目」）→ 用户否认一次，整套判断就崩。
- **把 `P-08` 写进项目文档** → 项目里长出第二套分类学；下次改 kit，项目那份就悄悄过期。

## 不做

- 不替用户做价值判断（「收不收」是他的事，你只给成本与后果）。
- 不装 `check-kit` 到目标项目（它需要 `principles/` 与 README 地图；目标项目只装 `cold-start-size`）。
- 不复制 kit 的正文到目标项目（复制 = 第二份会腐烂的副本；只复制模板与脚本）。
- 不在本 skill 里重做 `coldstart-intake` 的六步（它是本流程第 4 步里的一步）。
- **不和 `skills/extract-kit/SKILL.md` 抢「取一条」**：装 = 建整套薄面；取 = 只拿一条判据进已有体系。分不清时先问一句「这项目有没有自己的体系」。
