# L3 反例 · 04 门禁（A-07..A-09 · A-16 · A-23 · A-25）

> 反例 = **真实发生过的失效**，带实测数字 + 日期 + 出处。数字会漂 —— 本册的数字只作「当时的观测」，不作当前承诺。
> 每条四段：**现象** / **根因** / **正解（指向 P-NN）** / **怎么早发现**。
> 选条标准：**每个不同根因各一条**（本册现 6 条 = A-07 / A-08 / A-09 / A-16 / A-23 / A-25，六个根因），不把一个根因写成三条。

## A-07 只看末行 / 信转述的码 → 把红读成绿

- **现象**（两处实测）：① **另一项目 2026-09-20**（一次收尾写回）：把三棒符号锚并成一行（实测 **2829 字符**）→ `check-docs` 报 `FAIL 单行 >2000 字符`；主会话只取门禁输出末两行（末行恰好是另一条 WARN 明细）→ 直接提交推送，**FAIL 随提交进了远端**，下一轮才发现（随后拆分修复）。② **本方法仓 2026-10-30**：`tools.pwsh` 把 `node` 的 `process.exit(2)` 回传成 **1**；**2026-10-31 复现**，且命令链 `node …; echo "LAST=$LASTEXITCODE"` 的工具回传值是 **0**（真实 = 2）。
- **根因**：门禁有两个输出层 —— **给人读的判定行**与**给机器判的退出码**。「取末行」只取输出形状；「信工具回传」只取别人概括的码。两者都绕开了唯一能否决的信号，而失败**不报警**：绿读得很自然。
- **正解**：P-11（判定行 + 自己的码；三态；`2` 不是红）。
- **怎么早发现**：任何「我看过了 / 是绿的 / 通过了」的说法，追问两句 —— **FAIL 字样检索了吗？退出码是谁报的？**；读输出用 `Select-String "FAIL|WARN"`，不用 `-Last N`。

## A-08 把当时的观测写进断言

- **现象**（本方法仓 2026-10-30 两次实测）：① `version-mismatch` 态写死期望版本 `0.2.0-dev` —— 发版后 `CHANGELOG` 顶部正好是它 → **期望红、实得绿**；② 冷启动补白写死 `25,896` 字节 —— `README` 长大后直接**超硬门误报**（补白把总量顶过上限，与被测对象无关）。
- **根因**：断言值是**一次观测**（「我测的时候是 0.2.0-dev / 25,896 B」），不是**从当前状态推导**。项目一演进，断言与被测对象脱钩；两种脱钩都不报错。
- **正解**：P-13（相对当前值构造）。
- **怎么早发现**：断言里出现版本号 / 大整数 / 字节数，就问「**把项目升一版、把文档加长 10%，它还成立吗？**」；不成立 = 观测值。

## A-09 证明只做过一次

- **现象**（本方法仓 2026-10-30）：`selftest` 诞生前，注入故障是**一次性手工动作** —— 计划只要求「当轮实测会红」，没留配方与态 → 下一棒无法复跑（当时的偏离说明原文：「新增一个自证脚本：计划只要求一次性手工注入故障，下一棒无法复跑」）。同期两条探针（4 / 7）长期**没有独立注入态**却一直在册（**当时的登记** = D11「探针 4 / 7 缺独立注入态」；**现行登记面** = 留后登记面 §5「探针 4 缺独立注入态」行：「探针 4 与探针 2 面重叠：能让 4 红的输入也会让 2 红」）。**2026-10-31 补**：探针 7 已获独立态 `section-read-missing`（本棒），探针 4 仍缺。
- **根因**：把「证明」当成**一次动作**，不是**资产** —— 没有配方（怎么注入）、没有态（一条命令复跑）、没有隔离（是不是只有它能红）。一次性证明随会话消失，而门禁在下一代人手里继续发绿灯。
- **正解**：P-12（可复跑的注入态；做不到隔离就合并或记账，不假装）。
- **怎么早发现**：任何「已验证会咬」的说法，追问「**下一棒怎么复跑这一条？**」；答不出命令 = 只有一次观测。

## A-16 门量错了对象，还给你绿灯

- **现象**（2026-11-01 实测，一次真实接入）：在目标项目目录里跑 kit 的 `cold-start-size`（**不带 `--root`**），输出 `配置 = <副本>/kit.config.json` · `15584 B / 32768 B` · `OK` · **`LASTEXITCODE=0`** —— 它量的是**那份测试副本**（15584 属副本，不属 kit 本体），目标项目的三个文件**从头到尾没被量过**，而门给了绿。
- **根因**：脚本的「仓根」来自 `findRoot()` 从**脚本所在目录**向上找 `kit.config.json`，**cwd 完全不参与**；而操作者的心智模型是「量我脚下这个项目」。两者不一致时**没有任何提示** —— 判定行、字节数、退出码一应俱全，只是对象是别人。**门的结论没错，门判的不是那件事。**
- **正解**：P-11 + 本条的**前件** —— P-11 管「只认判定行 + 自己的码、且两者同一次」，但它**默认了判定行判的是你要判的对象**；本条补的就是这个前件。动作：跑任何门禁前先看判定行有没有点名对象（`配置 = …`），不对就加 `--root`。配套护栏（2026-11-01 落）：不带 `--root` 且 cwd 不在该仓内 → `exit 2` + 人话修法；协议命令一律写 `--root`（`skills/coldstart-intake` 第 2 步；脚本已拷进项目后那条 `node scripts/…` 属项目内自跑，不受此限）。
- **怎么早发现**：看判定行的第一行是不是**点名了它量的对象** —— 「配置 = …」指的不是你要量的那个仓 → 立刻加 `--root`。另一条通用问句：**「这条绿，是谁的绿？」**
## A-23 门是绿的，就以为这条做完了

- **现象**（本方法仓 2026-11-07 实测）：给外部评审的回执里写「两处模板已修」，实际两处原文一字未动；同一时刻本方法仓的门与构建期自足检查全绿 —— 一处落在 `<…>` 占位符里（检查整段跳过），一处是白名单名（`CLAUDE.md`）。抓到它的是外部评审逐条打开原文，不是门。
- **根因**：**主张的面 > 门的面**。门只覆盖它扫描的那一类；「已修」这句话覆盖的是**计划里的每一条**。两者不重合时，门绿是**无关证据**，却被当成完成证据。失败不报警：门确实跑了，也确实绿了。
- **正解**：`P-15`（门只覆盖可机械判定的一类，其余靠固定时点问句）+ `P-10`（结论要能复核）。动作 = 收尾核对**按计划清单逐条 grep 原文**；门绿只是清单里的一项。
- **怎么早发现**：每写「已修 / 已做 / 已覆盖」，问一句「**这一条在门的面内吗？**」不在 → 必须贴原文位置（`file:line`）或给出可复跑的证据，不许只报门色。

## A-25 门把调用者给的参照，当成了正确的参照

- **现象**（本方法仓 2026-11-07 实测，外部评审复现）：新加的自足门按「作者根」派生禁止名单。把一份**副本**或 **V2 自己**当作者根传进去 → 禁止名单为空 → 注入的明文**维护流程件引用**照样 **PASS**（exit 0）；只有传**本方法仓**才红（exit 1）。
- **根因**：门把「调用者给的参照」当成「正确的参照」，**没有校验它的身份**。参照错了，禁止集就空了 —— 门**看起来跑了**，实际什么都没测（`P-12` ③：从多个候选里挑错了对象）。这类失败最贵：它给的是绿，而绿的来源是「没东西可测」。
- **正解**：`P-12` ③ —— 参照参数必须**校验身份**（本仓 = 含维护流程三件 + 唯一的记录目录）；**禁止集为空 = exit 2**，不当作通过。
- **怎么早发现**：任何「拿外部树 / 外部配置当参照」的工具，问一句「**传错一棵，它会红还是绿？**」答「绿」= 这条门有身份洞。
