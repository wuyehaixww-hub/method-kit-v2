name: fit-kit
description: Use when someone has just got method-kit and has to decide whether and how it fits their own project — align both sides first (read the kit, scan the target with a bounded scan), then triage into 装 / 取 / 不用 and hand off a plan. 触发词：这套适合我吗、该不该用、装什么、适配、从哪开始、我项目要不要引入、先别装。
---

「适配」= **先量两边，再决定要不要穿**。产出 = 一份**适配计划**（决定 + 用哪几条 / 装哪几件 + 冲突点 + 复审触发）+ 一份**记录**（写给下一棒和三个月后的你）。

它不是「装」（`skills/adopt-kit/SKILL.md`），也不是「取」（`skills/extract-kit/SKILL.md`）：那两件是**执行**，本件只到「该走哪条路、第一步是什么」为止。

## 何时用

- 刚拿到 method-kit，想知道「我这项目要不要用、用哪几条」。
- 打算用，但不确定是「装」还是「取」、装几件。
- 手上有个项目，但**说不出一个具体失效**（`skills/extract-kit/SKILL.md` 的进门判据过不去）。

## 何时不用

- 已经确定要装整套 → 直接 `skills/adopt-kit/SKILL.md`。
- 已经有一个命名好的失效 → 直接 `skills/extract-kit/SKILL.md`（一次一条）。
- 要维护 method-kit 本身 → §0 答「维护」：包里有**维护者层**（分权 / 收尾 / 落点那张表）就走它；**没有** = 你拿到的是一份发布件，包内不可改，回它的上游改或 fork 后自建流程。

## 硬纪律（六条，越界即失败）

1. **不预设 kit 更好**：用户已有的方法论不因「来自 kit」而靠后。重复 / 矛盾 → 列出来 + 给推荐，**决定权归用户**；「不用」是合格答案（`P-05`）。
2. **先查再问**：能从仓里看到的，不许问用户（§2 的「能不能自己查」列）。
3. **只分诊，不执行**：装 / 取 的动作交给那两件协议；本件不写用户仓的文件（记录除外）。
4. **不复制判据**：只引 `P-NN` 编号，不搬正文 —— 两处书写 = `A-06`，而 `skills/` 没有内容探针，漂了不会红。
5. **不报时间，只报量**：说「要读 12 份文档 / 约 380 KB」，不说「两分钟搞定」——耗时取决于模型速率（40–70 tok/s 与 200 tok/s 差 3–5 倍）。
6. **「不知道」有三层兜底**（§3），不许静默假设。

## §0 定位（三件；两件能自答）

| 问 | 怎么得到 | 注意 |
|---|---|---|
| 这次是**维护**这个包，还是**把它用进你的项目** | 必问，一句话 | 维护 → 看包里有没有维护者层（分权 / 收尾 / 落点）：有就指它、本次结束；没有就说明「这是发布件，包内不可改」，本次结束（两种都**不访谈**） |
| 目标项目在哪 | **按顺序自答两步**：① cwd 是不是**方法仓本身**（包根同时有 `kit.config.json` 与 `skills/`）？是 → 目标另问，**别把包自己当目标** ② 不是 → cwd 是一个仓吗（有 `README.md` / `.git` / `CLAUDE.md`）？ | ② 是 → 报给用户确认；② 不是 → 问路径；**还没建** → 先问寿命 / 体量 / 难度 |
| **这一份方法仓**放在哪 | 必问，三选一 | 保留不动 / 挪到项目旁边 / **放进项目内**。放进去**必须警告**：用户自己的门禁会把**它**的文件一起扫（容量档 / 死链 / 编号），可能当场变红 |

> **必问 ≠ 逐字问**：开句已明确回答的，可直接采信并在记录里写「按开句推断」，**别重复问**；但「这一份方法仓放在哪」**不可跳过**（放进项目内会污染用户门禁）。

> **语言**：用用户的语言工作 —— 从开句判断；判断不了就问一句（**不新增第 7 问**）。核心术语按 `GLOSSARY.en.md`（包内有则用）。

## §1 对表（先入口 → 再体量 → 再决定扫多深）

### 1.1 入口哨兵（必读；≤3 个文件）
仓根的 `README.md` / `CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` 里**前三个存在的**。它们通常写着「规则正文在哪」—— 这就是「延伸面」的入口，比猜目录名可靠。

### 1.2 体量快照（只列不读；配置文件按 §1.4 读，但不计入份数）
排除 `.git` / `node_modules` / `vendor` / `dist` / `build` 与生成物，按类计数：
- **文档类**（`.md` / `.txt` / `.rst`）：份数 + 总字节 ← **决策只看这一类**
- **代码类**：源码扩展名的文件数（与文档分开，避免「项目大 = 规则多」的误判）
- **资源 / 生成物**：图片、二进制、锁文件、超大目录
- **顶层目录**（≤15 个）+ **最大的 5 个文件**

**份数只数文档类**；manifest / CI / lint 这些配置文件**要读、但不计入份数** —— 否则 30 / 150 的档位会被悄悄改掉。

### 1.3 扫多深：四档（默认「标准」；份数是量，不谈时间）

> 体量只决定**默认取哪一档**，不决定上限。档位买的是「能看到多少事实」，**不是「结论更准」**——裁决主要由用户意图决定（§2 第 1 / 2 / 5 问）；深度只多买一类事实：**能否看到一次可指认的失效实例 / 已有重复**，而这一类确实可能改变裁定（§4 第一 / 第二行）。**别把「更深更准」当承诺**。

| 档 | agent 读什么 | 份数 | 买到 | 输出必须写 |
|---|---|---|---|---|
| **轻** | 入口哨兵（§1.1）+ 体量快照（§1.2，只列不读） | ≤3 | ① 体量 ② 入口自述的体系 | 「我只看了入口」 |
| **标准（默认）** | + 延伸面里最像规则文的几份，按 `##` 大纲取节 | ≤5 整读 | + 已有规矩的分布、重复 / 冲突 | 「读了哪几节 / 没读哪节」 |
| **深** | + **形状扫描**：约束文档的标题 / 首段 / 表头，**不读正文** | ≤30 扫形 + ≤8 整读 | + 一次能指认的失效实例 | 「形状覆盖 N 份，正文只读 M 份」 |
| **超大** | 分工扫描：派只读子代理（`skills/subagent-dispatch/SKILL.md`）或开新会话 → 原料 → 简报（**协议待建**：尚无成文协议） | 不限 | 同上，分工完成 | 分工方案 + 原料清单 |

**默认怎么定**：文档 ≤30 份且 ≤300 KB → **标准，不必问**；31–150 份或 ≤2 MB → **先报量 → 停 → 问一句**（轻 / 标准 / 深）；>150 份或 >2 MB 或有多份 >200 KB → 建议**深**或**超大**，**并明说「这个体量我一次读不完」**（说完再给方案，别替用户决定），同样报量后问。**用户跳过 = 按标准走**，记录里写「未答」。

**份数是累计的**：标准档的 ≤5 **含**轻档的 ≤3；深档的 ≤8 整读**已含在** ≤30 扫形里。

**两处纪律不变**：**别只读开头 30 行** —— 失效常在文件后半（`P-04` 按节读）；**拿不到文件系统**（纯聊天 / 无读权限）→ 降级：请用户贴入口文件 + 3 份关键规则文档，或直接按 §2 问。

**形状扫描不是捷径**：标题写得像规矩、正文其实是笔记 —— 所以「扫形」之后仍要写「正文只读了几份」。

> **单文件读不完 / 文档在长** → 走 `skills/doc-governance/SKILL.md`（先测读上限，再按 `P-32` 四问决定拆不拆；本件只管「装 / 取 / 不用」）。

### 1.4 扫描纪律
**只读**：不跑用户的门禁、**不写用户仓的文件（记录除外，见 §5.2）**。**读到 §1.3 那一档的份数上限就停并汇报**，别顺着一路读下去。每条事实带出处（文件 + 行），别写「大概有」——`P-24`。

**代码面：三分界（默认不读实现）**

| 类 | 读不读 | 例子 |
|---|---|---|
| 声明式 | **要读** | manifest / CI 配置 / lint·format 配置 / 提交规范 / `CODEOWNERS` / migrations 清单 |
| 契约层 | **要读** | schema / openapi / proto / 类型定义 |
| 规则类代码 | 可读（按节） | CI 里调的脚本 / 钩子 / 自研 lint 插件 / 生成器 |
| 实现正文 | **不读** | 业务逻辑 / 组件 / 数据模型 / 算法 |
| 测试正文 | 只读**文件名 + `describe` / `it` 标题** | —— |

**破例通道**（业务语义只写在实现里时；默认关闭）：① **谁开口** —— 用户主动要求，或你先问并**明确得到「可以」**（「没反对」不算）；② **先说后读** —— 一句话讲清读哪几个文件 / 为了回答哪个问题 / 可能改变哪个结论；③ **读完点名** —— 计划与记录里写「我读了实现：<文件>（为了判断 X）」。上限 ≤3 个文件、按节读（`P-04`）；只准回答「这条业务规则 / 契约是什么」，**不准评价代码质量**（硬纪律 3）。

**业务语义的取法顺序**：① 用户自己说 —— **另问一句「这条规则在你这儿防的是什么」**（§2 的 Q2 / Q3 只问「最怕什么 / 最近一次失效」，不问业务规则本身）→ ② `README` 的「这是什么」+ 契约层 → ③ 前两条都答不出，才走破例。

**数字与行号只抄不算**：份数 / 字节 / 提交数各给一条当场命令的输出；**同一场里出现两个不同的数 = 停手重算**；引用的行号必须来自带行号的读取，写完回读那一行一次，贴回来的必须是引的那句。给用户看的选项里**不放没跑过的数**。
**只读了部分** → 计划里必须写「读了哪几节 / **未读哪节** / 影响是什么」（`P-30` 的分支；不写 = 结论建在没读的那部分上）。

## §2 问（6 问；一次一个；附属小问题可并组；每题带默认）

| # | 问什么 | 能不能自己查 | 用户答「不知道」时 |
|---|---|---|---|
| 1 | 这个项目要做到什么程度（做完就扔 / 会改几次 / 长期养） | ❌ 意图 | 给三档 + 我的推荐（「我猜 B：因为你有提交历史但很稀」） |
| 2 | 最怕哪种坏结果（无所谓 / 改坏对外契约 / 丢数据） | ❌ 价值 | 换场景句：「最怕**别人在用的东西被改坏**，还是**自己的数据没了**？」 |
| 3 | 最近一次「本不该发生却发生了」的事，要一个实例 | ⚠️ 半查（git log / 已有记录里找线索） | 我列 3 个候选让他勾；都不像 → 记「暂无实例」 |
| 4 | 现在有没有已在用的规矩 / 文档 | ✅ **扫描**（§1 已得到） | **不问**：直接报「我看到 X / Y / Z，对吗？」 |
| 5 | 谁拍板、谁执行（你 / 你听建议 / AI 执行你抽查） | ❌ 只有他知道 | 给三档 + 默认（copilot） |
| 6 | 愿意为「以后省事」现在投入多少：**最小面**（只管住第一屏 + 一道字节门）/ **常规**（+ 会话流程 / 坑索引 / 提示词骨架）/ **全量**（+ 收尾 / 交接 / 台账 / 证据地图）—— 三档各带「装几件 + 每件维护动作」半句 | ❌ 只有他知道 | 换场景句：「你更在意『现在别多事』，还是『以后少踩坑』？」仍答不出 → 默认**常规**，记录里标「未答」；**不按时间问、不报耗时**（硬纪律 5） |

**跳过 = 采纳默认**（每题都写默认）；**一次只问一个** —— 前一个的答案会决定后几个问什么、问多细（Q1 的答案决定 Q6 该给哪三档）；**只有同一问下的附属小问题**（不影响后续走向的补充项）可以并成一组：**≤3 个、把「丢了它这条结论就不成立」的那个排第一、每个都带推荐**；**任何一项未答 / 超时 = 按默认走，并在计划与记录里标「未答」**。问满 6 个就收，别加问。

> **为什么不一锅端**：问题堆在一起，agent 的描述会变粗、用户也理不清；而 6 问之间**有依赖**（前一问的答案会改后一问的问法）。诘问模板（`kit/templates/grill-decisions.md.template`）**更严：一律一问一答，连附属小问题也不并组**。

> **Q6 的三档是什么**：按**装几件的维护面**分，不按耗时 —— 最小面 = 冷启动面 + 字节门；常规 = + 会话流程 / 坑索引 / 提示词骨架；全量 = + 收尾 / 接力 / 台账 / 证据地图。件表真源 = `kit/intake/matrix.json` 的 `horizon`，本文件不复述。
>
> **本问只问「装多少」，不问「装不装」** —— 「取 1 条」是 §4 的裁定结果，不进本问；档名固定为 最小面 / 常规 / 全量，**不许改写成别的动作类型**。

## §3 「不知道」的三层兜底

1. **换说法**：术语 → 场景句（不问「你有没有判据」，问「有没有那种写着『目前 12 个文件』、过两个月就变错的句子」）。**再不行就用他项目里已有的东西打比方** —— 拿他的「最新版 / 定稿 / 交接清单」讲，比解释「判据 / 台账」省一半话。
2. **给选项 + 我的推荐**：不问开放题 —— 开放题是「不知道」的高发区。
3. **默认 + 留痕**：仍不知道 → 用默认值往下走，但在记录里单独标「用户不确定，按默认 X 处理；出现什么信号时回来看」（`P-14`：欠账要可枚举）。

**两个特殊态**：

- **没有人在场**（agent 自主跑，或用户只回「你看着办」）→ 每题按默认值走，并在计划抬头写明「**基于默认值 + 扫描事实，未经用户确认**」。
- **用户说的与扫描到的冲突**（他说有文档体系，你只看到两份 md）→ **两边都写出来**让他裁决，**不许静默采信任何一边**（自评只作待验，`P-19`）。

## §4 裁定（从事实推，不从偏好选）

| 对表得到的事实 | 裁定 | 交给谁 |
|---|---|---|
| **绿地**（判据 = `skills/adopt-kit/SKILL.md` 第 0 步；本文件**不复述**） | **装**（从最小件起） | `skills/adopt-kit/SKILL.md` + `skills/coldstart-intake/SKILL.md` |
| 有东西 + 有**已命名**的失效 | **取**（1 条；最多列 3 条候选） | `skills/extract-kit/SKILL.md` |
| 有东西 + **说不出**失效 | **先诊断**：用 §2 第 3 问的候选去命名；仍说不出 → **不用** | `skills/extract-kit/SKILL.md` 或「不用」 |
| 已有强方法论 + 与 kit 重复 / 冲突 | **列冲突 → 用户拍板**，取不重复的那部分 / 不用 | 记录 + `skills/extract-kit/SKILL.md` |
| 一两个人的一次性脚本 | **不用**（配额 0 合法） | 记录「不用 + 什么信号再来」 |

**多条同时命中时的优先级**（盲测实测：小项目 + 有已命名失效 ⇒ 两条都命中）：① **有已命名失效 → 取** ② 没有可跑的东西 → 装 ③ 其余 → 不用。

**「已命名失效」的判据不在本文件**（`skills/extract-kit/SKILL.md` 的**进门判据**写全，本文件不复制）；这里只加一条路由：**说不出「谁在什么时刻会出错、错成什么样」= 还没命名** → 回 §3 继续诊断；说得清就先往下走，实例（文件 / 日期）到 `extract-kit` 第 1 步再补齐 —— **别把「指不出行号」当「说不出失效」**。

**判据**：`装` 的影响面最大（会长期占他的目录），`取` 最小。**拿不准时选小的那个**，并在记录里写「先取，三个月后看」——可逆优先。

## §5 输出

### 5.1 适配计划（给用户看，≤20 行）

**每个裁定都要交代四件事**（装 / 取 / 不用 一视同仁；缺一条 = 没给结论）：

1. **我看到的** —— 至少一条扫描事实（份数 / 字节 / 已有的规矩 / 用户说的那次失效），带出处；**没看到的边界也写**（§1.4）。
2. **我套的判据 + 它和你怕的 X 对不对得上** —— 命中 §4 哪一行、那一行在防什么（**用人话，不报行号、不报编号**）；再说清它防的是不是你 §2 第 2 问答的那个「最怕」。**对不上就说「治不了」**，不许硬推荐。
3. **动作差** —— 装 / 取 会多做什么、不用 会少做什么；**说量不说时间**（硬纪律 5）。
4. **不装也能拿的（给 agent 的指令，不是给用户的链接）** —— 去读 `GUIDE.md` 的 §一 / §四 / §九（约 30 行），用你自己的话讲给他「这套东西在防什么」，再**从他项目里挑一处对应现象**；挑不出来就说「确实不需要」。**只丢链接 = 没做。**

**三条禁用写法**（写了等于没解释）：①「不适合你的项目」（没有事实）；②「详见 `GUIDE.md`」（把判断推回给一个不会去读的人）；③「等你项目长大了再说」（没给可判定的信号 —— 要写「出现哪种现象时回来」）。

### 5.2 记录（**默认写**；只有权限受限或用户明确不想写时才先问）
**记录是本件唯一允许写的文件**（除此之外不写用户仓任何文件）。默认直接落一份，落完告诉用户写了哪、为什么值得留（「不写的话，三个月后没人记得为什么只装了三件」）。用户当场说「别写」→ 不写，在对话里给结论并标「未落盘」。**先问的两种情形**：① 没有写权限 ② 用户明确说不想在仓里多文件。**路径三级**：`<记录目录>/` → `docs/` → **仓根** `fit-kit-<YYYY-MM-DD>.md`（前两个都没有就落根，并在计划里说明为什么放根）。**格式（10 行）**：

- 日期 · 目标仓 · 方法仓路径 · 基线（commit）
- 现状（扫出来的 3 条事实，各带出处）
- 决定（或**建议**）：装 / 取 / 不用 + **为什么**（§5.1 三段里最硬的那句）+ **谁拍的** —— 用户还没点头时必须写「建议：…（**待确认**）」，不许把默认推断写成「决定」
- **不装也能拿的**：指到哪几节 + 他挑出的对应现象（没挑出就写「没挑出」）
- 用哪几条（引 `P-NN` 前读过原文）/ 装哪几件
- 与已有方法的重复 / 冲突（有则列）
- 下一步：谁做、第一件事
- **装后多出的固定成本**（装 / 取 才写）：每次开工多读几份 / 多少字节（**材料字节，不是 GUI token**；口径见 `skills/coldstart-intake/SKILL.md` 的「按需估算」附录）、每次收尾多一张什么表
- 复审：日期或触发条件
- 没问到的 / 猜的（留白，`P-14`）

## 反例（都会真实发生）

- **没扫就问**：「你有没有文档体系」—— 有 `docs/` 的人觉得被小看，没有的人只会说「不知道」。**该看的东西先看**。
- **一路读下去**：从入口读进延伸面，又顺着引用读了二十份，最后忘了要回答什么。**读到本档的份数上限就停**（§1.3）。
- **报量了却没停**：数出份数之后接着往下读，等用户第一次听到那个数，已经读了十几份了。**报量 → 停 → 等他选**；他不答就按**标准**档走，并在记录里写「未答」。
- **把「不用」写成失败**：用户的项目小、问题已经被他自己的规矩治住了 —— 这时最诚实的话是「你现在不需要这套」，并写清什么信号出现时再来。
- **替用户拍板**：报告里写「建议装」没有问题；记录里写「用户决定装」但其实是自己选的就出事 —— 分不清谁决定的记录等于没有记录。**无人可问时更要说清**：写「建议（未确认）」，别写成既成事实。

## 不做

- 不装、不取、不改用户的仓（记录除外）。
- 不评估 kit 本身好坏（那是维护者的事）。
- 不承诺耗时；不承诺「扫完就能给你完整答案」。
- 不在用户没点头时给「你现在必须怎样」——给选项与后果，让他选。
